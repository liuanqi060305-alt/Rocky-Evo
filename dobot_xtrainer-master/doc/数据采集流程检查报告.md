# 数据采集流程检查报告

> 检查入口：`experiments/run_control.py`（遥操作 + 数据采集主程序）
> 检查目标：顺入口梳理涉及模块、各模块功能，重点排查**运行时 bug / 报错**。
> 说明：专有名词、变量名、函数名保持原文不翻译。文中标注 `文件:行号` 便于定位。

## 一、系统结构与数据流概览

本项目是**双臂遥操作 + 模仿学习数据采集**系统，采用「主从手」架构：

- **主手（leader）**：Dynamixel 舵机遥操作臂，人手操作，通过串口读关节角与按键。
- **从手（follower）**：两台 Dobot Nova 机械臂（`192.168.5.1` 左 / `192.168.5.2` 右），通过 TCP/IP 跟随主手运动。
- **相机**：3 台 RealSense（top / left / right），各开一个线程持续采图。
- **通信**：主程序 `run_control.py`（client）与 `launch_nodes.py`（server）之间通过 **ZMQ (REQ/REP)** 通信，server 端直连 Dobot。

**运行方式**：必须先起 `launch_nodes.py`（robot server），再起 `run_control.py`（采集 client）。二者是两个独立进程。

## 三、运行时问题清单（按严重程度排序）

> 图例：🔴 高（易崩溃/丢数据） 🟠 中（特定条件触发/数据质量） 🟡 低（健壮性/隐患）
> 每条标注：【已验证】= 读代码可确定；【疑似】= 需实机运行确认。

### 🔴 3.1 `servo_action_check` 的 assert 语义反了，正常动作也会崩溃 —【已验证】
`run_control.py:430-431`
```python
err3, action = servo_action_check(action, last_action, flag_in)
assert err3 != 0, set_light(env, "red", 1)
```
`servo_action_check`（`manipulate_utils.py:118-136`）的约定是：**动作正常返回 `1`，动作异常（跳变过大）返回 `0`**。
- 当动作正常（`err3==1`）：`assert 1 != 0` 通过 —— OK。
- 当动作异常（`err3==0`）：`assert 0 != 0` 失败 → **抛 `AssertionError`，主循环直接崩溃退出**。

问题点：
1. 这里用 assert 做“运行时安全保护”，一旦主手动作跳变（换向、丢步、通信抖动导致关节角突变）就整个采集进程崩掉，**当前正在录的这条数据直接丢失**。
2. `assert` 的第二参数 `set_light(...)` 只在断言失败瞬间求值，红灯点亮后进程随即退出。
3. 若以 `python -O` 运行，assert 被整体去除，**保护逻辑完全失效**，异常动作会直接下发给机械臂。

建议：改为 `if err3 == 0: set_light(env,"red",1); continue`（跳过本帧）或进入安全停止，而不是 assert 崩溃。

### 🔴 3.2 相机线程无异常保护，掉帧/掉线即杀线程并触发主循环 assert 崩溃 —【已验证】
`run_control.py:119-133`（`run_thread_cam`）内 `while 1` 循环体没有任何 try/except，`rs_cam.read()`（`realsense_camera.py:56`）在设备掉线/USB 抖动时 `wait_for_frames()` 会抛 `RuntimeError`。一旦抛出：
- 该相机线程**直接结束**；
- 主循环 `run_control.py:381-383` 的 `assert thread_cam_xxx.is_alive()` 随即失败 → **主进程崩溃**。

即相机任意一次读帧异常都会导致整场采集中断。建议线程内 try/except + 重试/重连，而非让线程静默死亡。

### 🔴 3.3 相机线程与主线程共享 `img_list` 存在数据竞争，且 dtype 不匹配 —【已验证 + 疑似】
- `img_list` 定义为 `np.array([...])`，元素是 `np.zeros((480,640,3))`，**默认 dtype 是 float64**（`run_control.py:116`）。
- 相机线程 `img_list[which_cam] = image_cam` 写入 uint8 图像；主线程落盘 `cv2.imwrite(..., img_list[0])`（`run_control.py:462-464`）。
- **竞争**：写 `img_list[which_cam]` 是逐元素拷贝 92 万个值，不是原子引用替换。主线程可能读到“写到一半”的帧（上下半张来自不同时刻）。【已验证：全程无锁】
- **dtype**：初始 float64，`cv2.imwrite` 对 float 有非预期行为；虽然相机线程跑起来后会被 uint8 覆盖，但**开始录制早于相机首帧写入时**会存到全 0/异常帧。show_img 分支用 `np.asarray(...,dtype="uint8")` 强转，落盘分支没有。【疑似：需实测首帧时序】

### 🔴 3.4 相机 encode 结果写入一维缓冲区，`npy_list` 形状不匹配会抛 ValueError —【疑似】
`run_control.py:131-133`：
```python
_, image_ = cv2.imencode('.jpg', image_cam, encode_param)   # image_ shape=(N,1)
npy_list[which_cam][:len(image_)] = image_                  # 目标 shape=(N,)
```
`cv2.imencode` 返回的是形如 `(N,1)` 的二维数组，赋值到一维切片 `(N,)` 上，numpy 广播会报 `could not broadcast`。若真触发，相机线程立即死亡 → 同 3.2 主循环 assert 崩溃。
注：`npy_list`/`npy_len_list` 在后续代码中**从未被读取**，是历史遗留死代码，但它仍在每帧执行、带崩溃风险。建议直接删除这两行。（标【疑似】是因为不同 OpenCV 版本 `imencode` 返回维度可能为 `(N,)`，需按实际版本确认。）

### 🔴 3.5 `ZMQClientRobot` 无接收超时，server 未启动/卡死则永久阻塞 —【已验证】
`robot_node.py:92-95` 创建 REQ socket 时未设 `RCVTIMEO`。`run_control.py:353` 连接后，一旦调用 `env.get_obs()/step()`（内部 `recv()`），若 server 进程没起或已卡死，`self._socket.recv()` **永久阻塞**，主程序无任何提示地挂起（`run_control.py:354` 那句“5 秒后检查网络”的提示其实没有对应的超时逻辑）。ZMQ REQ/REP 是严格“发-收”交替，一次 `recv` 卡住则后续全部卡住。建议设 `RCVTIMEO` + 重试/报错。

### 🟠 3.6 从手夹爪反馈恒为 1.0，采集到的 gripper 观测是“假值” —【已验证】
`dobot.py:97-113` `get_joint_state` 中，无论 `_use_gripper` 真假，`gripper_pos` 恒写死 `[1.0]`：
```python
if self._use_gripper:
    gripper_pos = [1.0]
    pos = np.append(robot_joints, gripper_pos)
else:
    gripper_pos = [1.0]
    ...
```
于是 `get_observations` 里的 `gripper_position` 和 `joint_positions[6]/[13]` 从机器人侧读到的**永远是 1.0**，并非真实夹爪开合。虽然 `run_control.py:471-472` 事后用 `action[6]/action[13]`（主手指令）覆盖了 `obs["joint_positions"]` 的夹爪位，但：
- `save_frame` 保存的 `obs["gripper_position"]` 仍是 1.0（未被覆盖）；
- 覆盖用的是“主手指令值”而非“从手实际值”，二者在夹爪有负载/延迟时并不相等。
实际夹爪位置本可通过 `self.gripper.get_current_position()` 读到（`dobot.py:87-95` 的 `_get_gripper_pos` 就是干这个的），但采集链路没用它。**结论：数据集中夹爪的本体感知通道不可靠。**

### 🟠 3.7 主手读线程内异常直接 raise，串口抖动即整只主手失效 —【已验证】
`driver.py:247-274` `_read_joint_angles` 后台线程：`txRxPacket` 通信失败时 `continue`（尚可），但 `isAvailable` 为假时直接 `raise RuntimeError`（`driver.py:268`）。该异常在后台线程抛出会**杀死读线程**，此后 `_joint_angles` 不再更新，`get_joints()`（`driver.py:277-284`）返回的永远是最后一帧旧值——主手“卡住不动”，且**主线程毫无察觉**（不会崩，只是数据静止）。这会导致采集到一段“主手不动、从手不跟随”的无效数据而无任何报错。

### 🟠 3.8 obs 与 action 存在一个控制周期的时序错配 —【已验证】
`run_control.py:449-473` 的顺序是：
```
save_frame(obs, action)      # 用的是上一轮 env.step 返回的 obs（t-1 时刻从手状态）
obs = env.step(action, flag_in)   # 之后才更新 obs 到 t 时刻
```
即每帧保存的是 `(obs_{t-1}, action_t)`：本体感知比动作**滞后一个周期（~40ms）**。而三路图像 `img_list` 是当前时刻（且由相机线程异步刷新，见 3.3）。因此单帧内“图像≈当前、proprio=上一拍、action=当前指令”，三者时间戳不统一。对模仿学习是数据质量隐患，建议先 `obs=env.step(...)` 再 `save_frame`，让 state/action/image 对齐到同一拍。

### 🟠 3.9 `is_falling` 传感器保护用 numpy 数组做 assert，多元素时会报歧义错 —【已验证】
`run_control.py:384` `assert not is_falling`，`is_falling = np.array([0])`（`:39`）。当前是单元素数组，`not np.array([0])` 可正常求值为 `True`。但：
- 一旦 `is_falling` 被改成多元素（或后续维护误改），`not np.ndarray` 会抛 `ValueError: truth value of an array ... is ambiguous`。
- `assert not is_falling` 语义脆弱，依赖“恰好单元素”。建议写成 `assert not is_falling[0]`（与 `button_monitor_realtime` 里 `while not is_falling[0]` 一致）。
另外传感器保护 `using_sensor_protection=False`（`:38`）默认关闭，且 ini 里 `using_sensor=0`，该保护链路当前整体未启用。

### 🟠 3.10 `flag_in` 依赖“先长按开 servo”才被定义，顺序异常时 UnboundLocalError —【已验证/边界】
`flag_in` 只在 `run_control.py:407/424` 的按键事件分支里赋值，却在 `:430` 和 `:470` 的 servo 执行分支里使用。正常流程中「长按开 servo」事件必然先于「servo 执行」，故 `flag_in` 已存在。但若 `what_to_do[*,1]` 的置位与 `dev_what_to_do` 的边沿检测出现异常错序（例如按键线程与主线程竞态、或状态被外部改动），`:428` 的 `if (what_to_do[0,1] or what_to_do[1,1]) and start_servo:` 可能在 `flag_in` 尚未定义时进入 → `UnboundLocalError`。属边界脆弱点，建议在 `main` 开头初始化 `flag_in = np.array([0,0])`。

### 🟡 3.11 网络请求无超时 + `eval()` 解析，固件/型号检查可能卡死或崩溃 —【已验证】
`run_control.py:291-323` 的 `get_firmware_version_satisfied` / `get_robot_type`：
- `requests.post(...)` **均未设 `timeout`**，机器人 IP 不可达时会长时间阻塞（默认无限等）。
- `get_robot_type`（`:305-312`）没有 try/except，且用 `eval(response.text)` 解析返回体：返回非预期内容时既有崩溃风险，也是**代码注入风险**（应改用 `json.loads`）。
- 版本号解析 `:295` 是一长串 `split` 链，返回格式稍变即 `IndexError`。
- 逻辑上 `get_robot_type` 失败返回 `None`，但 `robot_type` 之后传给已注释掉的 `calculate_vel_pos`，当前不触发，属潜伏隐患。

### 🟡 3.12 相机/按键线程在固件检查之前启动，早退时线程泄漏、进程无法退出 —【已验证】
`main` 里启动顺序为：相机线程（`:338-340`）→ 按键线程稍后（`:370`）→ **然后**才 `check_firmware_version()`（`:355`）。若固件检查失败 `return`（`:356`），3 个相机线程仍是 `while 1` 且**非 daemon**，会一直运行，主进程无法正常退出（需强杀）。按键线程 `while not is_falling[0]` 同理。建议把校验前置到起线程之前，或将这些线程设为 daemon。

### 🟡 3.13 `get_keys` 兜底返回伪造的“全松开”状态，可能触发假释放事件 —【已验证】
`agent.py:64-72`：连续 500ms 读不到合法按键时，`BimanualAgent.get_keys` 返回 `[[1,1,0],[1,1,0]]`（即两个 A/B 都为“松开=1”）。`driver.py:291-298` 的单手兜底则返回上次值或 `[1,1,0]`。在 `button_monitor_realtime` 的边沿检测里（`dev_keys = now_keys - last_keys_status`），若上一拍某键为“按下=0”、这一拍兜底成“松开=1”，会被识别成一次**假的释放事件**，可能误触发锁定切换/录制开关。串口偶发丢包时存在误动作风险。

### 🟡 3.14 `DynamixelDriver` 初始化的 assert 恒为真，等于没校验 —【已验证】
`driver.py:150-151`：
```python
self._torque_enabled = True
assert not self.set_torque_mode(self._torque_enabled), "fail set torque"
```
`set_torque_mode`（`:225-240`）**无返回值**（返回 `None`），`not None == True`，assert 恒通过。这句既没起到“确认使能成功”的作用，还有副作用：初始化时**默认给主手上了力矩**（`_torque_enabled=True`）。若期望开机主手是松的，这里与预期相反。

### 🟡 3.15 采集主循环内的安全保护整段被注释 —【已验证】
`run_control.py:433-446`：速度限幅 `check_pose_protection`、关节安全 `check_joint_safety` 全部被注释掉。当前采集期间**仅剩 3.1 的 `servo_action_check`（单帧跳变检查）在起作用**，没有工作空间/速度/J3 关节的保护。若这是有意为之（调试），建议在文档/代码里显式标注；若非有意，属安全缺口。

### 🟡 3.16 `BimanualAgent.set_torque` 与 `Agent` 协议签名不一致 —【已验证】
协议 `Agent.set_torque(self, _flag=False)`（`agent.py:19`）只有一个参数；`BimanualAgent.set_torque(self, which_hand=2, _flag=False)`（`agent.py:55`）是两个。调用处 `run_control.py:398` 用 `agent.set_torque(i, not what_to_do[i,0])` 是按双参数调的，功能正常，但协议定义与实现不符，靠鸭子类型侥幸工作，易误导后续维护。
