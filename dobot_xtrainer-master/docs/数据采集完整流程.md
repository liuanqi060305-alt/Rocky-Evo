# X-Trainer 数据采集完整流程

从开机到产出可训练清单的**唯一操作路径**。照着从上往下做即可。

最后更新：2026-09-10 · 采集程序 schema_version=2

- 硬件操作细节（灯语、按钮、对齐姿态）→ `doc/遥操作与数据采集操作手册.md`
- 目录职责与数据流转 → `docs/XTRAINER_DATA_FLOW.md`
- 字段语义与量纲 → `DATA_CONTRACT.md` / `DATA_AUDIT.md`
- 训练与推理 → `~/RockyEVO/openpi/examples/xtrainer/README.md`

## 0. 全流程一张图

```
阶段 A 开机自检          ← 每次开机做一遍
      ↓
阶段 B 采集              ← launch_nodes + run_control，Button B 一次 = 一条 Episode
      ↓
      ├─ 这条做失败了 → 当场 reject-human → 写轻量日志 → 删除原始 Episode
      └─ 这条做成功了 → 什么都不用做，留在盘上即可
      ↓
阶段 C 一条命令出清单     ← build-train-manifest（自动审查 + 出清单）
      ↓
阶段 D 交付 VLA          ← Converter 只读 train_manifest.json 里的 Episode
```

**核心策略：留存即成功（implicit success）。**

失败的 Episode 在采集后立即删除，所以磁盘上留下的**按定义就是成功示范** —— 不需要逐条人工标注 `success`。常规流程只有两条命令：失败时 `reject-human`，采完 `build-train-manifest`。

**三条硬规则：**

1. **失败必须当场删。** 这是「留存即成功」成立的前提。攒着不删 = 污染训练集。
2. `success`（任务成不成）默认 true，只有显式写 `false` 才排除；`valid`（数据够不够格）由程序判。两者语义不同，不可混用。
3. `valid=null` ≠ `valid=false`。前者是**还没审查**，后者是**已判定为坏数据**。审查失败的数据**不自动删**，等人工确认 —— 审查规则本身会误判。

## 阶段 B：采集

### B1. 启动 robot server（终端 1，保持开启）

```bash
conda activate x_trainer
cd ~/RockyEVO/dobot_xtrainer/dobot_xtrainer-master
python experiments/launch_nodes.py
```

本步使能两台从手并初始化夹爪（夹爪会开合一次），然后阻塞等 client。**从手此时不会移动。**

### B2. 启动采集主程序（终端 2）

```bash
conda activate x_trainer
cd ~/RockyEVO/dobot_xtrainer/dobot_xtrainer-master
python experiments/run_control.py

🔴 **安全点**：本步第 5 阶段 `robot_pose_init` 会让**从手自行缓慢运动**到初始姿态。启动前人手和身体离开机械臂工作范围。

看到 `-------------------------Ok, let's start------------------------` 即就绪。

常用参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--project-name` | `plug_and_unplug_task` | 数据集版本目录名。**每批新数据必须改**，见 §B5 命名规范 |
| `--save-data-path` | 空（走统一配置层） | Raw 根目录。留空即 `data/raw`，正常不用填 |
| `--show-img` | `False` | 显示相机画面。会占 CPU，正式采集建议关 |
| `--auto-video` | `True` | 录完自动后台生成三路拼接 `replay.mp4`，不阻塞控制循环 |
| `--robot-port` | `6002` | 需与 `launch_nodes.py` 一致 |

### B3. 操作序列

```
握稳主手 → 短按 Button A 解锁 → 拖动主手对齐从手姿态
        → 长按 Button A 开跟随（黄灯）
        → Button B 开始录制（绿灯）→ 做任务 → Button B 停止（回黄灯）
        → 重复采下一条
        → 长按 Button A 关跟随 → Ctrl+C 退出
```

| 灯 | 含义 |
|---|---|
| 灭 | 未开始跟随 |
| 黄 | 遥操作中，**未录制** |
| 绿 | **正在录制** |
| 红 | 出错（多为主从手偏差过大 / 动作跳变过大），重新摆姿再长按 |

**一次「Button B 开 → 关」= 一条 Episode = 一个时间戳目录。**

必须先长按开 servo（黄灯），Button B 才录得上。解锁主手前务必先握稳，否则力矩归零瞬间会因重力下坠。

### B4. 落盘结构

```
data/raw/<project_name>/collect_data/<时间戳>/
    ├── topImg/       0.jpg 1.jpg ...   顶部相机
    ├── leftImg/                        左腕相机
    ├── rightImg/                       右腕相机
    ├── observation/  0.pkl 1.pkl ...   joint_positions / control / timestamp_ns / monotonic_ns
    ├── meta.json                       Episode 元数据
    └── replay.mp4                      三路拼接回放（auto_video=True 时）
```

### B5. 数据集版本命名

用 `xtrainer_<任务>_v<N>[_debug|_full]`，例如 `xtrainer_pin_v0_debug` / `xtrainer_pin_v1` / `xtrainer_pin_v2`。

**禁止** `final`、`final2`、`new`、`latest`、`最终版`、`最新版`。

> 既有目录 `plug_and_unplug_task` 早于本规范，**不重命名**（`repo_id`、norm stats 路径、`episodes_to_delete.txt` 都引用它）。下一批启用新命名。

### B6. 第一条采完必须验一次

```bash
export XTRAINER_TASK_NAME=xtrainer_pin_v2_debug   # 后续所有命令都读这个
python scripts/manage_episodes.py list
```

确认新采的那条：`schema` 列是 `2`，帧数在 300–800，大小合理。然后看它的 `meta.json`：

```bash
python - <<'EOF'
import json, os, glob
from scripts.data_paths import paths
task = os.environ["XTRAINER_TASK_NAME"]
g = sorted(glob.glob(str(paths.collect_dir(task) / "*" / "meta.json")))
if not g:
    raise SystemExit("没有 meta.json —— 要么还没采，要么是 V1 旧数据")
m = json.load(open(g[-1]))
print(g[-1])
for k in ("schema_version", "num_frames", "duration_s", "fps_measured",
          "success", "valid"):
    print(f"  {k:<16}{m.get(k)}")
EOF
```

`fps_measured` 应该有值（实测约 18 Hz，**不是** 25）。如果是 `null`，说明时间戳没写进去，先停下来查，别继续采。

### B6.1 位置泛化采集与标注

同一个操作任务在不同物体位置采集时，模型语言指令必须保持一致。例如原数据使用
`plug and unplug`，新位置仍使用这个 prompt；不要改成 `plug at left`、`plug at right`。
物体位置应由图像决定，位置标签只写进 `meta.json`，用于采样平衡和泛化评估。

先在桌面固定一个参考原点和坐标约定：`x` 向右为正、`y` 远离机器人为正、`z`
向上为正、`yaw` 从上往下看逆时针为正。每个位置使用固定编号，例如：

| position_id | dx (mm) | dy (mm) | yaw (deg) | split |
|---|---:|---:|---:|---|
| `p00_center` | 0 | 0 | 0 | train |
| `p01_left` | -30 | 0 | 0 | train |
| `p02_right` | 30 | 0 | 0 | train |
| `p03_near` | 0 | -30 | 0 | train |
| `p04_far` | 0 | 30 | 0 | train |
| `p05_diag_holdout` | 20 | 20 | 0 | test |

位移数值应以现场安全工作区为准；表格只演示命名方式。泛化测试必须按**位置**留出，
不能把同一位置的一部分 episode 随机分到 train、一部分分到 test。

每移动一次插座/夹具，重启采集程序并带上这一组固定标注：

```bash
python experiments/run_control.py \
  --project-name xtrainer_plug_position_v1 \
  --position-id p01_left \
  --position-object socket \
  --position-frame table_reference \
  --position-dx-mm -30 \
  --position-dy-mm 0 \
  --position-dz-mm 0 \
  --position-yaw-deg 0 \
  --position-split train
```

该进程采下的每条 episode 都会自动包含：

```json
"generalization": {
  "factor": "object_position",
  "object": "socket",
  "position_id": "p01_left",
  "reference_frame": "table_reference",
  "offset_mm": {"x": -30.0, "y": 0.0, "z": 0.0},
  "yaw_deg": 0.0,
  "split": "train"
}
```

如果进程已经启动或已有几条数据没有自动标注，可按 episode 补写，且不会改变
`success` / `valid`：

```bash
python scripts/manage_episodes.py --task xtrainer_plug_position_v1 label-position \
  20260922101501 20260922101603 \
  --position-id p01_left --dx-mm -30 --dy-mm 0 --dz-mm 0 --yaw-deg 0 \
  --split train
```

补标后可用 `manage_episodes.py ... list` 在 `position` 列查看中文说明。脚本还会在
`data/raw/<task>/position_views/<位置编号>__<中文说明>/` 下创建按位置分组的软链接，
便于从文件名直观看数据；原始 timestamp episode 目录不会被改名或复制。

转换成 LeRobot 时给整批数据显式指定与原任务完全相同的 prompt：

```bash
uv run examples/xtrainer/convert_xtrainer_data_to_lerobot.py \
  --raw-dir /home/iml/RockyEVO/data/raw/xtrainer_plug_position_v1 \
  --repo-id xtrainer/xtrainer_plug_position_v1 \
  --generalization-split train \
  --prompt "plug and unplug"
```

转换器默认只转换 `split=train`，未标注的历史 episode 按 train 处理。留出的测试位置
要单独转换到另一个 repo，不能与训练集使用相同输出目录：

```bash
uv run examples/xtrainer/convert_xtrainer_data_to_lerobot.py \
  --raw-dir /home/iml/RockyEVO/data/raw/xtrainer_plug_position_v1 \
  --repo-id xtrainer/xtrainer_plug_position_v1_test \
  --generalization-split test \
  --prompt "plug and unplug"
```

## 阶段 B7：失败的当场删掉

**这是整套流程唯一需要人工介入的地方，也是「留存即成功」的前提。**

做失败了（没插进去 / 夹爪掉了 / 轨迹走错 / 中途误操作）就当场删，**不要攒着**。攒到几十条以后你分不清哪条是哪条，也就没法保证盘上留存的都是成功示范。

成功的那些**什么都不用做**，留在盘上即可。

`XTRAINER_TASK_NAME` 已导出的情况下所有命令不用带 `--task`。否则加 `--task <版本名>`，注意它是**全局参数，必须放在子命令前面**：

```bash
python scripts/manage_episodes.py --task xtrainer_pin_v2_debug list   # ✓
python scripts/manage_episodes.py list --task xtrainer_pin_v2_debug   # ✗ 报错
```

### 删除失败条目

```bash
python scripts/manage_episodes.py reject-human 20260910143022 \
    --reason operator_failure --note "夹爪没夹住，插头掉了"
```

`--reason` 是自由文本，建议固定用这几个：`operator_failure`（操作员失误）/ `task_failed`（任务没完成）/ `wrong_trajectory`（轨迹走错）/ `misoperation`（中途误操作）。

执行顺序（不可颠倒）：路径闸门 → 打印完整路径+帧数+占用 → **交互确认，须手动输入 `DELETE`** → 写日志并 fsync + 回读校验 → 删除目录 → 验证已不存在。

日志写不成功就直接退出，**不会删数据**。

留下的记录在 `data/rejected/<版本>/rejected_log.jsonl`（同时写一份 `.csv` 便于表格查看），只含 `episode_id / time / reason / source / success / num_frames / size_mb / note`，**不留任何图片、视频、pkl 副本** —— 人工失误轨迹不占硬盘。

脚本批量场景可加 `--yes` 跳过交互，**手动操作时不要用**。

### 事后才发现不该用？

已经采完一批、事后才发现某条有问题但暂时不想删：

```bash
python scripts/manage_episodes.py mark-failed 20260910143022 --reason task_failed
```

写 `success=false`，**保留数据但排除训练**。想彻底删还是走 `reject-human`。

改错了要撤销：

```bash
python scripts/manage_episodes.py mark-success 20260910143022
```

`mark-success` 在留存即成功策略下**只用于撤销 `mark-failed`**，正常采集不需要它。

### 随时看状态

```bash
python scripts/manage_episodes.py list
```

```
episode_id        success     valid     frames  schema  size
20260910143022    true*       None      412     2       31.4 MB
20260910143055    true        True      388     2       29.8 MB

```

## 阶段 C：一条命令出训练清单

```bash
python scripts/manage_episodes.py build-train-manifest
```

它一步做完两件事：

1. **自动审查**所有 `valid=null` 的条目（即所有还没审过的），把结论写回 `meta.json`
2. 生成 `data/raw/<版本>/train_manifest.json`

收录标准 `success != false AND valid != false` —— 也就是「没被显式判失败，也没审查不合格」。

典型输出：

```
发现 8 条未审查，先自动审查

20260910143022: PASS
  -> meta.json: success=True, valid=True
20260910143055: FAIL
  - rightImg 有 1 个空文件: 10
  -> meta.json: success=True, valid=False, quality_issues=['empty_image_file']
...
审查完成: PASS=7  FAIL=1
[quality] 1 条质量不合格 -> .../quality_rejected_manifest.json

[train-manifest] 7 条可训练 -> .../train_manifest.json
  排除 1 条:
    20260910143055  quality_rejected  success=True valid=False ['empty_image_file']
```

审查同时会把隐式 success 落成显式 `success=true` + `success_source="implicit_retained"`，让 `meta.json` 自解释 —— 下游读它的人不必先知道「留存即成功」这条策略。

这是 `train_manifest.json` 的**唯一**生成方式。Converter 读它，不读磁盘上有什么。

`--no-audit` 可跳过自动审查只出清单，但那样会把未审查数据收进去（清单里 `unaudited` 字段会列出来，终端也会告警）。正常不要用。

### C1. 单独跑审查

不想出清单、只想看审查结果：

```bash
# 审查所有留存且 valid=null 的
python scripts/manage_episodes.py audit-pending

# 单条
python scripts/manage_episodes.py audit 20260910143055

# 只看结果不写 meta.json（试跑）
python scripts/manage_episodes.py audit-pending --no-write

# 强制全部重审（改过阈值后用）
python scripts/manage_episodes.py audit-pending --all
```

判定引擎是 `scripts/episode_audit.py`，五类检查：

| 类别 | 内容 |
|---|---|
| 图像 | 三路目录存在性、jpg 数量、编号连续性、空文件（逐帧）、可解码性+纯黑（首/中/尾+均匀抽 20 帧） |
| Observation | pkl 数量与编号连续性、可读性、`joint_positions` / `control`、V2 的 `timestamp_ns` / `monotonic_ns`、`schema_version` 一致性 |
| 长度 | 四模态帧数一致 **且帧号集合逐一比对**（数量相同也可能错位）、300–800 区间 |
| 数值 | NaN / Inf（报具体帧号）、`(T,14)` 维度、夹爪 ∈[0,1]、关节 \|θ\|<2π、动作跳变 |
| 时间戳 | 两个时基各查单调性 / 重复 / 倒退 / >0.5s 间隔；输出 `duration_s` 与 `fps_measured` |

`errors` 非空 → FAIL → 写 `valid=false` + `quality_issues`。`warnings` 不影响判定，只提示。

**关于动作跳变阈值**：提示级 0.17 rad（≈10°）、硬错级 0.35 rad（≈20°）。0.17 原本是 `run_inference.py` 的**推理期**安全闸门（防模型输出狂暴动作），不是人工遥操作的质量标准 —— 操作员本来就会快速移动。实测既有 episode 关节增量 p50=0.44°、p99=7.75°、峰值 10.02°，且峰值处是一段连续快动而非孤立尖刺。硬错级取物理上界（18.3Hz × 180°/s ≈ 9.9°/帧）的约 2 倍。

### C2. 审查失败的数据怎么办

**不会自动删。** 只写 `valid=false`，同时登记到 `data/rejected/<版本>/quality_rejected_manifest.json`。

因为审查规则本身可能误判（上面那个 0.17 阈值就是实例）。人工确认确实是坏数据后再显式删：

```bash
python scripts/manage_episodes.py delete-invalid 20260910143055 --reason "右腕相机全黑"
```

这条命令要求目标 `valid` 已经是 `false`，`valid=true` 或 `null` 会被拒绝。

### C3. 跨条分布概览

```bash
python scripts/check_episodes.py
```

回答「整批数据长什么样」：帧长分布桶、状态-图像对齐、丢帧统计，末尾第 4 节是与 `audit` **完全一致**的 PASS/FAIL 汇总（共用同一引擎，不会给出矛盾结论）。它**只读**，不写 `valid`。

> ⚠️ `scripts/delete_bad_episodes.sh` 是 `check_episodes.py` 每次运行都会**覆盖重写**的历史遗留产物，里面是一串 `rm -rf`，没有路径校验，且 `cd` 的目标是上一次运行时的目录。**不要用它删数据**，删数据一律走 `manage_episodes.py`（有七道路径闸门 + 日志先行）。

## 5. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 卡在 `Waiting to connect the robot...` | server 没起、端口不一致，或网络/TCP-IP 模式问题。ZMQ client 无接收超时，会一直等 |
| 连接机械臂超时 | 多余网卡上残留 `192.168.5.x` 抢路由。重启会复现 |
| 红灯，长按无法开跟随 | 主从手偏差过大。松手重新摆姿对齐再长按 |
| 按 Button B 没录上 | 没先长按开 servo（必须是黄灯状态） |
| `list` 里 `schema` 是 `1` | 从旧副本 `~/dobot_xtrainer/` 启动的采集程序。切到 `~/RockyEVO/dobot_xtrainer/` |
| `fps_measured` 是 `null` | 时间戳没落盘。停下来查，别继续采 |
| `build-train-manifest` 结果为空 | 所有条目都 `valid=false`。看终端排除原因，多半是同一个系统性问题（比如某路相机全黑） |
| 某条不该进训练但已采完 | `mark-failed <id> --reason ...`（保留数据）或 `reject-human`（彻底删） |
| Converter 打 WARNING 说没有清单 | 先跑 `build-train-manifest` |
| 图像偏暗 | 相机 90fps 上限压了曝光时间。30fps 下实测亮度 +78%~+102% 且不增噪，但**改 fps/曝光会改变数据分布，要在正式采集前一次定好** |
| VS Code 集成终端里 `sudo` 失效 | snap 版带 `NoNewPrivs=1`。开系统终端 |

## 6. 不要做的事

- **不要把失败的 Episode 留在盘上过夜。** 整套「留存即成功」建立在「失败当场删」上，攒着不删就等于把失败数据喂进训练
- 不要从 `~/dobot_xtrainer/` 旧副本启动正式采集
- 不要手动 `rm -rf` Episode 目录 —— 走 `manage_episodes.py`，它有七道路径闸门和日志先行保证
- 不要在 `data/raw` 里做格式转换、覆盖或原地修改。Raw 采完即视为不可变
- 不要自动删除 `valid=false` 的数据。审查规则会误判，必须人工确认
- 不要把「人工遥操作失误」和「VLA/RLT 自主推理失败」混为一谈。后者是重要数据资产，不适用删除策略，另行设计
- 采集中途不要改相机 fps / 曝光 / 控制频率，会让同一批数据分布不一致
- 大文件（`*.ckpt` `*.pth` `*.mp4` `*.hdf5`、raw / lerobot 数据）不进 Git

## 附录：与旧版流程的差别

早先的版本要求每条成功数据都跑一遍 `mark-success`，`build-train-manifest` 只收 `success == true AND valid == true`，审查和出清单是两条命令。

在「失败当场删」的前提下，逐条 `mark-success` 是纯冗余劳动 —— 已改为留存即成功。变化：

| | 旧 | 新 |
|---|---|---|
| 成功数据 | 每条跑 `mark-success` | 什么都不用做 |
| 收录标准 | `success == true AND valid == true` | `success != false AND valid != false` |
| 审查 | `audit-pending` 单独一步，且要求 `success=true` | `build-train-manifest` 自动带上，只看 `valid=null` |
| 常规命令数 | 每条 1 次 + 收尾 2 次 | 只有失败时 1 次 + 收尾 1 次 |

`mark-success` 命令保留，语义改为「显式覆盖」，只在撤销 `mark-failed` 时需要。旧数据兼容：`success=null` 现在被视作 true，因此之前没标注的 Episode 不必回头补标。
